# 1. Rebranding Objective

The existing Innovatrix application is being rebranded as **CoSetup**.

This is primarily a **brand evolution, not a complete product redesign**.

The existing application's structure, UX patterns, marketplace functionality, customer-request workflow, vendor functionality, service offering, and overall visual direction should be retained unless a change is specifically required by this document.

The objective is to:

1. Replace Innovatrix branding with CoSetup.
2. Establish a consistent CoSetup visual identity.
3. Rewrite customer-facing language where necessary to reflect the CoSetup positioning.
4. Preserve the clean, premium, minimal design language already present in the application.
5. Make the platform understandable to non-technical customers without alienating developers and software vendors.
6. Position CoSetup as more than a source-code marketplace.

Do not redesign working interfaces simply for the sake of making them different.

# 3. What CoSetup Is

CoSetup is a software marketplace and services platform designed around a simple principle:

> Businesses usually need working software, not merely source code.

Customers can use CoSetup to:

* discover ready-made software;
* evaluate and preview solutions;
* purchase software;
* request modifications to existing software;
* submit requirements for software they cannot find;
* commission custom development;
* obtain installation and configuration assistance;
* arrange deployment and DevOps services;
* obtain cloud/infrastructure assistance;
* request migrations and integrations;
* receive ongoing technical support;
* arrange software maintenance;
* use managed services where appropriate.

Software vendors and developers can use CoSetup to distribute their products and provide associated services.

CoSetup therefore sits between a traditional software marketplace, development agency, freelance marketplace, and managed software provider.

It should not be presented as merely another place to download scripts.

# 4. Core Brand Idea

## Software, set up for you.

This is the central idea behind CoSetup.

A customer might not have to understand:

* which programming language they need;
* which framework should be used;
* which database architecture is appropriate;
* which cloud provider should host the application;
* whether an existing product can satisfy 80% of the requirement;
* whether something needs to be built from scratch.

The customer should be able to describe the **business outcome** they need.

CoSetup helps determine the appropriate route.

This may mean:

**Find it.**
An appropriate solution already exists.

**Fit it.**
An existing solution can be customised.

**Build it.**
A new solution is required.

**Launch it.**
The software needs configuration, infrastructure or deployment.

**Run it.**
The customer requires hosting, maintenance or ongoing support.

# 5. Brand Positioning

## Primary positioning

**CoSetup helps businesses find, customise, launch and maintain the software they need.**

The marketplace is the starting point, not necessarily the end of the relationship.

Traditional code marketplaces commonly follow:

**Discover → Purchase → Download**

CoSetup extends this:

**Discover → Evaluate → Purchase → Clarify → Deliver → Configure → Test → Support → Maintain**

The existing nine-stage lifecycle currently represented in the product can therefore remain.

For marketing communication, however, simplify the concept wherever appropriate.

Preferred simplified language:

> **Find it. Fit it. Launch it. Run it.**

Alternative campaign language:

> **Find it. Build it. Run it.**

These are marketing devices and should not replace detailed workflow terminology where precision is necessary.

# 11. Brand Voice

CoSetup communicates primarily in **clear, conversational professional English**.

The customer should feel as though they are speaking with a highly capable technical partner who knows how to explain technology without making the customer feel technically inadequate.

## Example

Avoid:

> Specify your preferred technology stack and database architecture.

Prefer:

> Tell us what you need the software to do.

Avoid:

> Submit a bespoke software development requirement.

Prefer:

> Can't find what you need? Tell us about it.

Avoid:

> Additional deployment and infrastructure management services are available.

Prefer:

> Need help getting it live? We can handle that too.

Avoid:

> Leverage our ecosystem of pre-built software solutions.

Prefer:

> There's a good chance someone has already built most of what you need.

Avoid:

> Purchase and download source code.

Prefer:

> Get the software — and the help you need to get it running.

# 12. Tone by Context

CoSetup has one voice but adjusts its tone according to context.

## Marketing

Clear, confident and benefit-oriented.

Example:

> Find software that already does most of what you need. Customise what's missing and get help taking it live.

## Marketplace

Useful and factual.

Prioritise:

* what the software does;
* who it is for;
* what is included;
* what can be customised;
* requirements;
* support;
* pricing;
* demo availability.

## Requirements / Custom Build

Conversational and reassuring.

Example:

> Tell us what your business needs to do. You don't need to know the technical details.

## Vendor interfaces

Professional and more technically precise.

Technical terminology is acceptable where vendors reasonably understand it.

## Infrastructure / DevOps

Precise and transparent.

Do not hide technical implications when they materially affect cost, security, reliability or maintainability.

## Errors

Human and actionable.

Avoid:

> Error 500. Request processing failed.

Prefer:

> Something went wrong while processing your request. Please try again.

Where appropriate, provide a next action.

# 23. Marketplace Philosophy

CoSetup should encourage reuse before unnecessary redevelopment.

Core principle:

> **Start with what exists. Build what's missing.**

When an existing product satisfies a substantial portion of a customer's requirements, CoSetup should make it easy to:

1. discover it;
2. evaluate it;
3. preview/demo it;
4. identify gaps;
5. request modifications;
6. purchase it;
7. customise it;
8. deploy it;
9. maintain it.

Custom development remains available when no appropriate starting point exists.

This is not anti-custom-development.

It is **anti-unnecessary-redevelopment**.

# 24. Custom Requests

Customers should be able to submit requirements without first identifying a specific marketplace product.

The customer describes the desired business outcome.

CoSetup can then determine whether:

* an existing marketplace product fits;
* an unlisted vendor product substantially fits;
* an existing product should be customised;
* multiple services are required;
* a completely custom solution is appropriate.

The interface should therefore avoid language suggesting customers must know the implementation route before submitting a request.

# 30. UX Writing Principles

Every piece of UI copy should answer at least one of these questions:

**What is this?**
**Why should I care?**
**What happens next?**

Buttons should generally describe actions.

Prefer:

**View demo**

instead of:

**Click here**

Prefer:

**Request customisation**

instead of:

**Submit**

Prefer:

**Continue to checkout**

instead of:

**Next**

where context benefits from specificity.

Avoid unnecessary explanatory text where the interface is already obvious.

CoSetup should be clear, not verbose.

# 31. Rebranding Implementation Instructions

When implementing this rebrand:

### Phase 1 — Audit

Inspect the repository and identify:

* branding components;
* logo components;
* colour tokens;
* typography tokens;
* SEO metadata;
* page metadata;
* manifests;
* favicon assets;
* OpenGraph assets;
* email templates;
* notification templates;
* PDFs/documents generated by the application;
* footer/header references;
* legal pages;
* configuration;
* seed/demo content;
* tests containing brand assertions.

Produce a concise implementation plan before changing files.

### Phase 2 — Brand Tokens

Consolidate reusable brand values.

Where architecture permits, create central values for:

* brand name;
* canonical domain;
* primary colour;
* dark colour;
* background colours;
* logo assets;
* support/contact identity where appropriate.

Avoid scattering hard-coded branding unnecessarily.

### Phase 3 — Visual Rebrand

Replace:

**Innovatrix → CoSetup**

and update the logo system.

Retain the current visual structure unless changes are required for consistency.

### Phase 4 — Copy Review

Do not merely replace the company name.

Review major customer-facing copy against this document.

Rewrite wording where the old copy:

* overemphasises scripts;
* sounds overly technical;
* makes CoSetup appear to be only a marketplace;
* fails to communicate services;
* contradicts the CoSetup positioning.

### Phase 5 — Metadata

Update:

* page titles;
* meta descriptions;
* canonical URLs;
* OpenGraph data;
* Twitter/social metadata;
* manifests;
* structured data;
* favicon references;
* application names.

### Phase 6 — Communications

Update customer-visible:

* transactional email branding;
* notifications;
* onboarding messages;
* vendor communications;
* generated documents.

### Phase 7 — Verification

Search the repository again for all variations of:

**Innovatrix**

and manually evaluate every remaining occurrence.

Run:

* lint;
* type checks;
* automated tests;
* production build;
* relevant integration/E2E tests.

Do not consider the rebrand complete merely because the homepage says CoSetup.

## Preserve what already works.

Do not use this rebrand as justification to:

* restructure unrelated components;
* rewrite unrelated business logic;
* replace the design system;
* change database architecture;
* rename internal concepts unnecessarily;
* introduce a new framework;
* redesign every page;
* add unnecessary dependencies.

Changes should be deliberate and scoped.

Where a branding change exposes an obvious inconsistency, fix it.

Otherwise preserve working behaviour.

# 33. Desired Customer Impression

After visiting CoSetup for the first time, a customer should understand:

> **I can find software here.**

Then:

> **If it isn't exactly what I need, they can help adapt it.**

Then:

> **If what I need doesn't exist, I can request it.**

And finally:

> **They can also help me deploy and keep it running.**

That progression is the essence of CoSetup.

> **I can sell software here.**

> **CoSetup can create additional commercial opportunities beyond the original software sale.**
